# Kafka-контракты E-Bank v1

Документ фиксирует формат и правила доставки событий между сервисами User, Money и Antifraud. Источником истины для структуры сообщений являются JSON Schema из каталога [`schemas`](schemas/), а готовые сообщения приведены в [`examples`](examples/).

## События и маршрутизация

| Событие | Producer | Consumer | Topic | Kafka key |
| --- | --- | --- | --- | --- |
| `LoginSucceeded` | User | Antifraud | `user.security-events.v1` | `data.userId`, UTF-8 |
| `FraudCheckRequested` | Money | Antifraud | `money.fraud-check.requested.v1` | десятичная строка `data.transferId`, UTF-8 |
| `FraudDecision` | Antifraud | Money | `antifraud.decision.made.v1` | десятичная строка `data.transferId`, UTF-8 |

Ключ `userId` сохраняет порядок событий безопасности одного пользователя. Ключ `transferId` стабильно направляет повторные доставки события одного перевода в одну партицию. Kafka key не входит в JSON payload и передаётся отдельно в записи Kafka.

## Общая оболочка

Каждое сообщение имеет одинаковую верхнеуровневую структуру:

```json
{
  "eventId": "019a5d20-7ac0-7000-8000-000000000001",
  "eventType": "FraudCheckRequested",
  "eventVersion": 1,
  "occurredAt": "2026-11-08T12:00:00Z",
  "data": {}
}
```

| Поле | Тип | Обязательное | Назначение |
| --- | --- | --- | --- |
| `eventId` | UUID string | да | Уникальный идентификатор логического события. Producer генерирует UUIDv7 один раз при создании Outbox-записи. |
| `eventType` | string | да | Тип события, зафиксированный соответствующей схемой. |
| `eventVersion` | integer | да | Версия payload. Для описанных контрактов всегда `1`. |
| `occurredAt` | RFC 3339 date-time | да | Время возникновения бизнес-события, а не публикации или получения сообщения. |
| `data` | object | да | Данные конкретного события. |

Producer должен формировать время в UTC с суффиксом `Z`. Consumer также должен принимать корректные RFC 3339 значения с часовым смещением.

Неизвестные дополнительные поля разрешены. Consumer обязан игнорировать неизвестные поля, чтобы добавление необязательных данных не ломало существующую версию.

## `LoginSucceeded`

Schema: [`login-succeeded-v1.schema.json`](schemas/login-succeeded-v1.schema.json). Пример: [`login-succeeded-v1.json`](examples/login-succeeded-v1.json).

Событие создаётся после успешной аутентификации и содержит данные, необходимые Antifraud для истории входов и географического анализа.

| `data` field | Тип | Обязательное | Назначение |
| --- | --- | --- | --- |
| `userId` | non-empty string | да | Непрозрачный Keycloak `sub`; формат UUID не навязывается. Бизнес-идентификатор события. |
| `ipAddress` | IPv4/IPv6 string | да | Клиентский адрес без маски подсети. |

`LoginSucceeded` не содержит `transferId`, поскольку вход не относится к процессу перевода. Его бизнес-идентификатором является `userId`.

Keycloak не является источником стабильного идентификатора устройства: из проверенного токена используется `sub`, а исходный IP передаёт доверенный Nginx. `deviceId` поступает от клиентского приложения при создании перевода и передаётся в `FraudCheckRequested`; именно этот контекст используется Antifraud для правил нового и общего устройства.

## `FraudCheckRequested`

Schema: [`fraud-check-requested-v1.schema.json`](schemas/fraud-check-requested-v1.schema.json). Пример: [`fraud-check-requested-v1.json`](examples/fraud-check-requested-v1.json).

Money создаёт событие в одной транзакции с переводом средств в `FRAUD_CHECK_PENDING`, резервированием суммы и записью Outbox.

| `data` field | Тип | Обязательное | Назначение |
| --- | --- | --- | --- |
| `transferId` | positive int32 | да | ID перевода Money и ID проекции `transfer_attempt` в Antifraud. |
| `fromAccountId` | positive int32 | да | Счёт отправителя. |
| `toAccountId` | positive int32 | да | Счёт получателя. |
| `senderId` | non-empty string | да | Keycloak `sub` владельца счёта отправителя. |
| `recipientId` | non-empty string | да | Keycloak `sub` владельца счёта получателя. |
| `amount` | decimal string | да | Положительная сумма в рублях, `numeric(19,2)`, ровно два дробных знака, например `"1000.00"`. |
| `deviceId` | string или `null` | да | Устройство, с которого создан перевод; `null`, если неизвестно. |
| `ipAddress` | IPv4/IPv6 string или `null` | да | IP, с которого создан перевод; `null`, если неизвестен. |
| `createdAt` | RFC 3339 date-time | да | Время создания перевода. |

`occurredAt` описывает время возникновения события, а `data.createdAt` — время создания бизнес-объекта. В текущем процессе они совпадают, но их семантика различна.

Денежная сумма передаётся строкой, а не JSON number, чтобы сериализация и десериализация в Go не приводили к потере точности.

## `FraudDecision`

Schema: [`fraud-decision-v1.schema.json`](schemas/fraud-decision-v1.schema.json). Примеры: [автоматическое решение](examples/fraud-decision-automatic-v1.json) и [решение аналитика](examples/fraud-decision-analyst-v1.json).

Antifraud публикует только окончательное решение.

| `data` field | Тип | Обязательное | Назначение |
| --- | --- | --- | --- |
| `transferId` | positive int32 | да | ID проверенного перевода Money. |
| `decision` | `APPROVED` или `REJECTED` | да | Окончательное решение. |
| `riskScore` | integer 0..100 | да | Score автоматической проверки. |
| `source` | `AUTOMATIC` или `ANALYST` | да | Источник окончательного решения. |
| `triggeredRules` | array | да | Сработавшие правила автоматической проверки; пустой массив допустим. |

Каждый элемент `triggeredRules` содержит:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `ruleId` | integer 1..8 | Стабильный номер правила. |
| `score` | integer 1..100 | Вклад правила в итоговый score. |
| `reason` | non-empty string | Сохранённое объяснение срабатывания. |

В массив входят только результаты со статусом `TRIGGERED`. Результаты `NOT_TRIGGERED` и `SKIPPED` остаются в Antifraud и в событие не включаются.

При `source = ANALYST` поле `decision` содержит решение аналитика, а `riskScore` и `triggeredRules` остаются результатами первоначальной автоматической проверки.

### `REVIEW_REQUIRED`

`REVIEW_REQUIRED` является промежуточным автоматическим результатом и не входит в допустимые значения `FraudDecision.data.decision`. При таком результате Antifraud создаёт `review_case`, а перевод остаётся в `FRAUD_CHECK_PENDING`. Событие публикуется только после решения аналитика `APPROVED` или `REJECTED` с `source = ANALYST`.

## Доставка, повторные попытки и дедупликация

Обмен выполняется по модели **at least once**. Повторная доставка является ожидаемым поведением.

### Producer и Transactional Outbox

1. Бизнес-изменение и запись исходящего события в Outbox выполняются в одной транзакции PostgreSQL.
2. `eventId` генерируется при создании Outbox-записи и идентифицирует логическое событие, а не попытку отправки.
3. Все повторные публикации одной Outbox-записи сохраняют исходные `eventId`, Kafka key, `eventType`, `eventVersion`, `occurredAt` и `data`.
4. Producer не создаёт новый `eventId` после ошибки или тайм-аута Kafka.
5. Outbox-запись помечается опубликованной только после подтверждения Kafka. Временная ошибка приводит к повторной отправке той же записи.

### Consumer и Transactional Inbox

Consumer в одной локальной транзакции:

1. проверяет структуру и поддерживаемую версию сообщения;
2. вставляет `eventId` и исходный payload в Inbox с уникальным ограничением по `eventId`;
3. для нового события выполняет бизнес-изменение и отмечает Inbox обработанным;
4. для уже зарегистрированного события не повторяет бизнес-изменение;
5. фиксирует транзакцию до подтверждения Kafka offset.

Повтор с тем же `eventId`, но другим типом, бизнес-идентификатором или payload является нарушением контракта, а не допустимым дубликатом. Такое сообщение нельзя применять; расхождение должно быть записано в журнал и передано на разбор.

## Совместимость

Номер версии одновременно отражён в имени топика (`.v1`) и поле `eventVersion` (`1`).

В пределах `v1` разрешено:

- добавлять необязательные поля;
- уточнять документацию без изменения семантики;
- добавлять необязательные вложенные сведения;
- игнорировать неизвестные поля на стороне consumer.

Новая версия контракта и топика (`.v2`) требуется при:

- удалении или переименовании поля;
- изменении типа или семантики поля;
- превращении необязательного поля в обязательное;
- изменении представления идентификатора, времени или денежной суммы;
- добавлении enum-значения, которое существующий consumer не может безопасно обработать.

При переходе на новую версию producer при необходимости временно публикует обе версии до миграции всех consumers.

## Соответствие текущему SQL

SQL этапа 2 уже создаёт базовую оболочку и основные данные событий, но синхронизация с этим контрактом выполняется в PIGGYBANK-BACKEND-6.

| Область | Текущий SQL | Контракт v1 |
| --- | --- | --- |
| Envelope | нет `eventVersion` | обязательное `eventVersion: 1` |
| `FraudCheckRequested.amount` | JSON number | decimal string с двумя знаками |
| `FraudDecision.triggeredRules` | отсутствует | обязательный массив сработавших правил |
| Тестовые seed payload | старый формат | должны быть синхронизированы со схемами |

В рамках фиксации контрактов SQL-функции и seed-файлы не изменяются.
